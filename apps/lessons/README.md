# The lessons engine (PD-29 materials quality, P0-3)

A Chat-owned rebuild of the lessons site, written from scratch: nothing is copied from, installed from, or run from the old `jawwid-lessons` repo. Plan: `docs/product/pd029-materials-quality-plan.md`. Contract: `docs/product/quran-dataset-contract.md`.

- **Quran text:** only from the snapshot CI builds with `scripts/lessons/build-quran-snapshot.py`, which verifies `data/quran/` first. The engine re-verifies it and fails closed.
- **Lesson content:** `src/content/surah-NNN.json` holds a surah's reviewed prose (tafsir lines, word meanings, quiz, lessons learned) plus POSITIONS into the verified text (`{ayah}`, `{ayah, word}`), never Quran text. Nothing of a file is shown until the Teachers department approves it (`review.status`); a line with `review` set is never shown. `scripts/lessons/check-lesson-content.py` checks every position against the real dataset and refuses typed Quran in the prose; the engine refuses any file whose positions do not resolve. Al-Buruj (85) is the reference lesson.
- **Children's Quran content (PD-49, schema 2):** `src/content/quran/surah-NNN.json` (none yet) holds our own child-level prose per item -- intro, tafsir, word meanings (word spans), lessons, reflections, stories, themes, asbab, quiz -- each citing a public-domain work from `src/content/sources.json`, plus positions and `{{w:A:N[-M]}}` word tokens into the verified text. An item shows only with a fresh approval in `src/content/approvals/surah-NNN.json` (the SHA-256 of its canonical JSON, every required review step) and only when every work it cites has a pinned edition (none is pinned yet). Asbab show only under the display rule. `src/content/quran-content.ts` resolves it; `scripts/lessons/check-quran-content.py` checks it in CI. Plan: `docs/product/pd049-children-quran-experience-plan.md`.
- **Audio:** one controller per lesson, verse by verse. Recitation arrives only from the signed-in app that opened the lesson, after the API's release gate decided this account may have it (`src/audio/audio-manifest.ts`); every file is checked against its SHA-256 before it plays. Build-time `LESSONS_PARENT_ORIGINS` / `LESSONS_MEDIA_ORIGINS` (comma-separated https origins) fix who may send it and where files come from; unset, the build has no audio. No student hears anything until the owner records the licence.
  - The audio list is **data only**: `{ type: 'jawwid:quran-audio', surah, ayahs: [{ ayah, audio: { reciter, key, url, sha256 } }] }`, at most 286 entries. Any unknown field anywhere refuses the whole list. It carries no credential or token other than the short-lived signed URLs, and no Quran text: the opener sends only `ayah` and `audio` from each `/quran/ayahs` entry.
- **Builds:** production builds come only from CI (the `lessons-dist-<sha>` artifact). Locally, `npm ci --ignore-scripts`, `npm run typecheck` and `npx vitest run --maxWorkers=2` only. `typecheck` needs the snapshot first (`vite.config.ts` imports its manifest as the build's trust anchor): `python3 -I scripts/lessons/build-quran-snapshot.py` from the repo root.
- **Supply chain:** guarded by `bash scripts/qa/guards.sh lessons-supply-chain`. Every locked release must be at least 7 days old (CI's release-age step warns otherwise). `overrides` in `package.json` holds transitive packages (rollup, postcss, `@babel/*`, the browserslist family) at exact releases past that cooldown; to move one, re-lock from scratch (`npm install --package-lock-only --ignore-scripts` with no old lockfile) and check the release age again.
- **Hosting:** its own origin; see `deploy/headers.md`.
