# Jawwid Chat

A customer communication and customer operations system for Jawwid Online Quran & Arabic Academy. Familiar like WhatsApp, owned and operated by Jawwid.

Version0.1**Draft for review**

Date5 September 2026

OwnerMohamed Lasheen

Working nameJawwid Chat (placeholder)

StatusRequirements agreed in discovery; stack and integration pending confirmation

## 1Summary

Jawwid runs on continuous communication with parents: classes, teachers, subscriptions, payments, renewals, follow-ups. Today that runs on WhatsApp, where the relationship, the history and the phone number belong to the employee, not to Jawwid. Jawwid Chat replaces WhatsApp for parent communication with a mobile app Jawwid owns end to end.

One Family → One Primary Owner. *People can change. The customer experience shouldn't reset.*

The product has two halves that ship together. The first is a messaging app for parents on iOS and Android whose everyday experience (chat list, chat screen, media, voice notes, read receipts, typing, replies, reactions, search, calls) is close enough to WhatsApp that a parent needs no training. The second is an operations layer for Jawwid's supervisors and manager: a web inbox built around families rather than phone numbers, permanent customer ownership with shift coverage, workload and attention visibility, tasks and follow-ups, automated reminders driven by the existing Jawwid system, and full management visibility of every conversation.

This is explicitly **not** a layer on top of the WhatsApp Business API and not a WhatsApp clone for its own sake. Every feature is judged by one question: does it make customer communication and operations better than WhatsApp for Jawwid?

**What the MVP delivers.** Reliable 1:1 chat with push notifications; Family accounts; Student Groups with a simple approval policy; enforced communication permissions; an automated reminder engine (classes, payments, renewals, schedule changes); in-app voice calling (1:1 for admins, group calls inside Student Groups); the Admin Inbox with ownership, shift coverage and workload monitoring; tasks and follow-ups; and a Manager Dashboard. Labels, broadcast, the full approval workflow, AI attention scoring and fallback channels move to Phase 2 (section 13).

## 2Context

### 2.1 Jawwid

Jawwid is an online Quran and Arabic academy for children. Each family is served by an assigned supervisor who handles onboarding, scheduling, teacher coordination, payments, renewals and complaints. Classes are delivered online by teachers. The operational data (students, parents, teachers, schedules, subscriptions, payments) lives in an existing internal system, referred to here as **Jawwid Core**.

### 2.3 Product boundaries

- Internal product for Jawwid in this phase. Not multi-tenant, but the data model carries an `organization_id` on every root entity from day one so a future SaaS conversion is a migration, not a rewrite.
- Jawwid Core remains the source of truth for students, parents, teachers, schedules, subscriptions and payments. Jawwid Chat integrates through an API or a dedicated integration layer, never by reading Jawwid Core's database directly (section 12.4).
- Jawwid's existing brand (logo, colours, typography) is applied throughout. The UI is familiar like WhatsApp, but clearly Jawwid; no WhatsApp branding is copied.

## 3Roles & access

Access is role-based (RBAC) and enforced on the server for every read and write. Roles are additive with scopes: an admin sees what belongs to her work; a manager sees the department.

Identity inside the app is **name, profile and role**. Phone numbers are stored for account and support purposes only and are never rendered to another user, never included in an API response to a non-admin, and never used as a display identifier.

## 4Core business rules

These rules are the constitution of the product. They are enforced in backend authorization and in database constraints, not by hiding buttons. A direct API call that violates a rule is rejected with an audited error. No future feature may contradict them unless the rule itself is explicitly changed and re-versioned here.

**BR-1 · No direct Teacher ↔ Parent communication**

Teachers and parents communicate only inside the official Student Group, where the assigned admin/supervisor is a member. A teacher cannot start, send, or receive a private conversation or call with a parent; a parent cannot start one with a teacher. Creating such a conversation, group, or call is rejected server-side regardless of client.

**BR-2 · Phone numbers are never exposed**

No user sees another user's phone number, in chat, profile, search, call screens, notifications or exports. Calls are placed through Jawwid's in-app calling layer using Jawwid identities.

**BR-3 · Communication follows relationships**

Who can talk to whom is derived from Jawwid Core relationships (family, enrollment, ownership, coverage) and the communication matrix below. There is no open directory. Teachers cannot message parents outside their assignments; teacher-to-teacher messaging is permission-controlled and off by default.

**BR-4 · One family, one primary owner**

Every family has exactly one primary owner (an admin) at any time. Ownership is permanent until the manager reassigns it. Coverage and workload routing let other admins handle a family's conversations without changing ownership.

**BR-5 · History belongs to Jawwid**

All conversation, call and task history is owned by the system, retained when people leave, and visible per RBAC. Nothing is deleted when an employee is deactivated or a family changes owner.

**BR-6 · Admin and manager messages publish immediately**

Messages from admins, coverage admins and managers never require approval. Approval policies apply only to teacher and parent messages in groups and are configurable per group type.

**BR-7 · Official messages come from Jawwid**

Automated reminders and system messages are sent under the official **Jawwid** identity. 1:1 conversations show the name of the person handling the family alongside the Jawwid identity. Parents can reply to official messages; the reply lands in their normal conversation with Jawwid.

**BR-8 · No end-to-end encryption in this phase**

"Protected messages" means approval and visibility control, not E2EE. Jawwid must be able to moderate, support, audit and troubleshoot. All traffic is encrypted in transit and all stored data is encrypted at rest, with strict access control and audit logging.

## 5Operating model

Jawwid does not want a shared queue. The system is built on **permanent customer ownership + shift coverage + workload monitoring**. The owner keeps the relationship; the system makes sure the owner is never a bottleneck.

### 5.1 Ownership

```
Family ──▶ Primary Owner (admin)          e.g. Dina owns 200 families

Normal shift:   parent message ──▶ owner's inbox
Off shift:      parent message ──▶ coverage admin's inbox (owner unchanged)
Overloaded:     manager sees it on the dashboard and can route or reassign
```

- Ownership is assigned when a family is created (synced from Jawwid Core or set by the manager) and changed only by a manager, with a reason, recorded in the audit log.
- When an admin leaves or is deactivated, the system lists every family she owns, blocks deactivation until the manager picks a new owner or backup per family (or in bulk), transfers ownership and preserves all history. The manager is alerted whenever any family has no active owner.

### 5.2 Shift coverage

A coverage schedule maps owner → coverage admin by time window and weekday. The initial configuration reflects today's operation and is fully editable by the manager:

| **WindowOwnersCoverage**    |                            |                                                   |
| --------------------------- | -------------------------- | ------------------------------------------------- |
| Night (outside owner shift) | Dina, Zeinab               | Coverage admin A (Maryam or Radwa — configurable) |
| Night (outside owner shift) | Rehab, Asmaa               | Coverage admin B (configurable)                   |
| Friday (all day)            | Dina, Zeinab, Rehab, Asmaa | Maryam                                            |

- Coverage is time-based by default, and can also be triggered manually (owner marks herself unavailable) or by policy (owner workload reaches Critical, see 5.3).
- A conversation handled under coverage is labelled as such in the thread and the family timeline, so the owner sees exactly what happened while she was away, and the parent sees the same "Jawwid" conversation with a different named person.
- Coverage admins act with the owner's permissions on that family for the duration of the window, and nothing more.

### 5.3 Workload model

The number of families owned is not workload. Workload is computed from live activity, per admin, with configurable weights that the manager tunes after real operational data is collected:

```
workload_score = Σ weight[i] × count[i]   over:
  active_conversations, waiting_for_admin, follow_ups_due, sla_at_risk,
  new_conversations, open_tasks, renewal_cases, escalations
```

**LowMediumHighCritical**

Thresholds between states are configurable. State changes to High or Critical notify the manager; Critical can optionally open the owner's families to a coverage admin. The per-admin breakdown (as in "Dina · owned 200 · active 7 · waiting 3 · follow-ups 4 · SLA risk 1 · Medium") is shown on the Manager Dashboard and, for her own numbers, to each admin.

### 5.4 Attention model

Conversations carry an **attention state** rather than a static P1/P2/P3. In the MVP the state is rule-based; AI classification is added in Phase 2 as a suggestion that business rules can override, never the reverse for sensitive decisions.

| **StateTriggers (MVP rules)** |                                                                                                                                                                                                                                        |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Needs attention now**       | Message during or within 15 min of a scheduled class for that student; a service-blocking state in Jawwid Core (suspended subscription, failed payment); SLA about to breach; a complaint flagged by an admin; a message marked Urgent |
| **Needs attention soon**      | Renewal due within the configured window; follow-up due today; unresolved issue older than the configured threshold; task overdue                                                                                                      |
| **Normal**                    | Everything else: general questions, information requests, ongoing conversation                                                                                                                                                         |

Inputs to the state: message intent (Phase 2 AI, MVP keywords and manual flags), customer context from Jawwid Core, urgency flags, business impact (renewal value, at-risk status), SLA timers, and the family's current state. The state drives inbox ordering, notification priority, and dashboard counts.

## 7Functional requirements

### 7.1 Accounts, sign-in and sessions

- Sign-in with username and password provisioned from Jawwid Core. No self-registration. Accounts are created, activated and disabled from the admin panel or by sync.
- Multi-device sign-in is allowed. Each session is bound to a device record (platform, model, app version, push token, last seen). Users can see and sign out their own devices; admins can revoke any session; a disabled user loses all sessions within seconds.
- Password reset is handled by the admin (temporary password) in MVP; self-service reset by OTP over SMS/email is Phase 2.
- A parent account holds all children of the family. The chat list groups the family's Student Groups under the child's name; the "Jawwid" 1:1 conversation is pinned at the top.
- Rate limiting and lockout on failed sign-ins; short-lived access tokens with rotating refresh tokens.

### 7.2 Messaging (1:1 and group)

Message types

- Text (with links)
- Images (multiple)
- Video
- Voice notes (record, playback speed)
- PDF and files
- System messages (ownership changed, coverage active, class rescheduled…)

Behaviours

- Reply to a message
- Reactions
- Per-recipient sent / delivered / read status
- Typing indicator, online presence per policy
- Delete for me; delete for everyone within a configurable window (admins always)
- Search within a chat and across chats (scoped by RBAC)

Chat list

- Archive, mute, pin
- Unread counts and last message preview
- Attention and pending-approval badges
- Family / child grouping for parents

Reliability

- Offline compose queue with retry
- Idempotent send (client message id)
- Ordered delivery per conversation
- Media upload resumable; thumbnails generated server-side
- Configurable size limits per media type

Deferred: message editing, advanced forwarding, starred messages, Status, disappearing messages.

### 7.3 Student Groups

- One official Student Group per student, created automatically from Jawwid Core relationships: the parent, every assigned teacher, and the family's primary owner. Coverage admins join automatically during their coverage window (or are permanent silent members, configurable).
- Membership follows the data: a teacher change in Jawwid Core adds the new teacher and removes the old one, with a system message. A group is archived, never deleted, when a student leaves.
- Group names follow a template such as "Ahmed · Jawwid" and display the student's name and the members' names and roles. No member can add or remove members manually except managers.
- Group calls (section 9) are started from the group by teachers or admins; parents can join and, if policy allows, start one.
- Class Groups (a whole teaching group with several families) are Phase 2; the model supports them from the start via `conversation.type`.

### 7.4 Message approval (MVP: simple policy)

An approval policy is attached to each group type. The MVP policy has two switches, `teacher_requires_approval` and `parent_requires_approval`, each defaulting to on for Student Groups.

```
Teacher or parent sends in a Student Group
  → if policy requires approval: message stored as PENDING
      · visible only to the sender, marked "Pending approval"
      · visible to approvers in an Approvals queue and in the group thread
      · approver = the family's active handler (owner, or coverage admin during coverage)
      · push notification to the approver
      → Approve  → message PUBLISHED to all members, normal delivery and receipts
      → Reject   → message REJECTED; sender sees status and the reason
  → else: PUBLISHED immediately
Admin / manager messages: always PUBLISHED immediately
```

- Approval applies to every message type: text, images, video, voice notes and files.
- Approvers never edit a sender's message silently. If content needs changing, the approver rejects with a reason or replies in the group herself.
- Pending messages never expire automatically in MVP; they stay pending until decided and appear in the approval backlog on the dashboard.
- Phase 2 adds: escalation to the manager, configurable expiry, approver by shift and coverage rules, private reply to the sender from the approval screen, and per-group overrides.

### 7.5 Family account and Admin Inbox

The Admin Inbox is the supervisor's working surface on the web. It is organised by family and by attention, not as a flat chat list.

- Views: My families · Waiting for my reply · Under my coverage · Needs attention now · Follow-ups due today · Pending approvals · Unassigned (manager).
- Every conversation opens with the **Family panel**: parent, children, teachers, next class, subscription and payment status, renewal date, owner and current handler, open tasks, recent calls, labels (Phase 2), and the full timeline across all of the family's conversations.
- Handler actions from the thread: reply, assign a follow-up, create a task, flag as complaint, mark urgent, add an internal note (visible to staff only, never to the parent), hand off to another admin with a note, escalate to the manager.
- Conversation state: open / waiting on customer / waiting on Jawwid / resolved, with SLA timers per state, both configurable.
- Conversations created automatically by the system (onboarding, renewal, payment, schedule change, follow-up) land in the owner's inbox with their type shown.

### 7.6 Tasks and follow-ups

- Tasks belong to a family (optionally a student and a conversation), have an assignee, due date, type (follow-up, renewal, payment, complaint, onboarding, custom), status and notes.
- Follow-ups are lightweight tasks created from a thread in one action ("Follow up on Sunday"), surfaced in the inbox and on the dashboard, and reminded via push to the assignee.
- Automations can create tasks (for example, "renewal due in 7 days" opens a renewal task for the owner). Overdue tasks feed the workload score.
- When ownership changes, open tasks move with the family unless the manager decides otherwise.

### 8.3 Delivery, tracking and de-duplication

- Each notification instance carries a deterministic `dedupe_key` (for example `class_reminder:session_123:T-30m:parent_45`); the same key is never sent twice, even after a re-sync or a rule edit.
- Status timeline per instance: scheduled → sent → delivered (where the platform reports it) → opened → failed (with reason). Visible per family and aggregated on the dashboard.
- Reminders are also written as official in-app messages in the parent's Jawwid conversation, so the history is complete even if push fails; the parent can reply directly.
- Priority levels `normal` / `important` / `urgent`. Urgent uses a distinct sound and channel, bypasses mute where the OS allows, can escalate to the manager, and in Phase 2 can trigger a fallback channel per policy. SMS is never used per-message by default because of cost.
- Quiet hours per recipient locale; class reminders and incoming calls are exempt.
- Rule and template changes are versioned and audited.

## 11Non-functional requirements

### 11.1 Security and privacy

- TLS 1.2+ everywhere; encryption at rest for database, media storage and backups; media served through short-lived signed URLs.
- RBAC enforced in one authorization layer on the server; no client-side-only restrictions. Sensitive conversations can be restricted to manager and above.
- Audit log for: sign-ins and session revocations, ownership and coverage changes, approvals, message deletions, staff reads of conversations outside their own portfolio, rule and template changes, exports, and every denied action under BR-1 and BR-2.
- Phone numbers and other contact data stored in restricted columns exposed only to manager and super\_admin endpoints.
- No automatic message deletion in this phase; retention policy to be defined later on legal, cost and privacy grounds. Screenshot prevention is not an MVP goal.
- Secrets in a managed secret store; dependency and container scanning in CI; backups tested by restore.

### 11.2 Reliability and performance

- At-least-once delivery with idempotent message ids; no message loss on reconnect; per-conversation ordering.
- Targets for the initial scale: message fan-out under 500 ms p95 for online recipients; push dispatched within 2 s; class reminders fire within 60 s of schedule; call setup under 3 s.
- Reminder engine is exactly-once per dedupe key and safe to re-run after outages.
- Horizontal scaling path for the real-time layer without re-architecture (section 12).

### 11.3 Localisation

- Arabic and English in app and admin panel, with full RTL layout; the Arabic layout is a first-class design target, not a mirrored afterthought.
- All strings, templates and dates localised; Cairo timezone default with per-user timezone support for families abroad.

### 11.4 Observability

- Structured logs, metrics and traces; alerting on delivery failures, push failures, reminder lag, call setup failures and sync errors with Jawwid Core.

### 12.4 Integration with Jawwid Core

- A dedicated **integration service** owns all traffic with Jawwid Core. Preferred: Jawwid Core exposes an API and change webhooks. If not, the integration service polls or consumes a read replica through an explicit, documented contract; Jawwid Chat application code never touches Jawwid Core's database.
- Synced entities: users and roles, families, parents, students, teachers, enrollments and class sessions, subscriptions, payments and due dates. Each carries an `external_id` and `synced_at`; conflicts resolve in favour of Jawwid Core for its own fields.
- Change events (class rescheduled, payment overdue, teacher changed…) are emitted to the event bus and drive both automatic conversations and the reminder engine.
- Sync health (lag, errors, unmatched records) is visible in the admin panel and alerts the technical admin.

### 12.5 Enforcing the matrix in code and data

- Single `AuthorizationService.canCommunicate()` called by every conversation, membership, message, call token and search code path; unit-tested against the full matrix, including the forbidden Teacher ↔ Parent cases via direct API calls.
- Database constraint: a `direct` conversation may not have both a `teacher` member and a `parent` member (enforced by trigger/check on membership rows), so even a bug in application code cannot create the forbidden relationship.
- LiveKit room tokens are minted only after the same check; a client cannot join a room it was not authorised for.
- Search results, mentions, contact pickers and notification recipients are filtered by the same service.

### 13.1 Delivery milestones inside the MVP

Milestones are ordered by dependency and risk, not by feature glamour. Calling is the highest technical risk and starts as a spike in M1 so it is proven before it is scheduled.

- **M4 · Calling1:1 and group voice**CallKit / ConnectionService, VoIP push, history, call notifications.
- **M5 · ManagementTasks, workload, dashboard, hardening**Tasks and follow-ups, workload scoring, Manager Dashboard, audit, load tests, store submission.

A pilot with one supervisor's portfolio (for example Dina's families) runs after M3 with calling still on the existing process, then expands after M4. Dates are set after M0, when volumes and the integration path are known.
