accepts its kind's terms (`terms_family`, `terms_teacher`, `terms_staff`) and the shared

Build: ENG-09 the data model (slot 20261107110000, renumbered on 2026-11-07 from 20261104110000; this branch); ENG-10..12 the API gate, the
Flutter gate and the Admin Web gate.

ENG-09 engineering decisions (the lead's to review):
- **Strictly immutable.** The acceptance guard refuses every UPDATE and DELETE, with no erasure
  exception: §7.2 keeps acceptances through an erasure, and `chat.erase_account` anonymises the
  account row rather than deleting it. The account foreign key is ON DELETE RESTRICT, so an
  account that accepted can never be hard-deleted out from under its record. TRUNCATE is
  refused except in a test's cleanup (`chat.test_truncate`), as for PD-47/48/49/55.
  Consequence for ENG-10: a spec that records acceptances and then hard-deletes its accounts
  must first truncate `chat.terms_acceptance` in its cleanup transaction (add it to the
  harness's truncate list).
- **The database stamps the time** (`accepted_at`, `created_at`); a caller cannot backdate.
- **A-3 in the database too:** an acceptance of another kind's terms is refused by the guard,
  as a second line behind the API's "exactly the required set" check.
- **Publishing is idempotent for a retry** and refuses a changed version (publish a new one).
- **RLS fail-closed:** no request role writes either table or executes either writer; a
  signed-in account reads only its own acceptances (as PD-48's acknowledgements); versions are
  read by the server only.
- **The rollback refuses** while either table holds rows, unless the operator sets
  `chat.rollback_discards_terms` after exporting them: the rows are consent records.

L-ENG-1 (2026-11-07): the developer guide's §1.3 proposals P-1 to P-4
(`docs/legal/developer-implementation-guide.md`) are folded into this migration, before it merges,
so no second migration or parallel table is needed:
- **P-1** `legal_document_version.content_sha256_ar` / `content_sha256_en`: required, exactly 64
  lowercase hex characters (one canonical form, so the release check in §6.3 compares strings).
  They are arguments of `chat.publish_legal_version`, and the idempotent re-publish compares them:
  the same URLs over different text are a changed version and are refused.
- **P-2** `terms_acceptance.method` (`signup` | `gate`): a required argument of
  `chat.accept_legal_documents`, with no default, so the API always says which flow it is. A repeat
  acceptance keeps the first row's method, as it keeps its time.
- **P-3** `legal_document_version.requires_reacceptance boolean not null default true`: an
  argument of `chat.publish_legal_version` (default true), compared on a retry. **Decision:** the
  guard refuses `false` for a document that has no version requiring acceptance yet, so a
  document's first version always requires it and ENG-10's required set is never empty. ENG-10
  still fails closed if it finds no requiring version at or before `legal.current.<key>` (for
  example, through `effective_at` ordering): it then requires the version in force.
- **P-4** confirmed: no IP address, user agent or device identifier on `terms_acceptance`; a test
  asserts the exact column list and the absence of network-address types.

New signatures (ENG-10 callers, including the local branch `claude/pd58-terms-api`, must follow):
`chat.publish_legal_version(document_key, version, url_ar, url_en, content_sha256_ar,
content_sha256_en, requires_reacceptance default true, effective_at default null, created_by
default null)` and `chat.accept_legal_documents(account_id, documents, client, locale, method)`.
