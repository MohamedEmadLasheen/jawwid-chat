The owner approved A-3 (docs/release/google-play-blocker-roadmap-2026-11-03.md §7). Each account
accepts its kind's terms (`terms_family`, `terms_teacher`, `terms_staff`) and the shared
`code_of_conduct`. The wording, URLs and version names are pending (N-3): they are the owner's
configuration, never code or migrations.

Build: ENG-09 the data model (slot 20261107110000, renumbered on 2026-11-07 from 20261104110000; this branch); ENG-10..12 the API gate, the
Flutter gate and the Admin Web gate.

ENG-09 engineering decisions (the lead's to review):
- **Strictly immutable.** The acceptance guard refuses every UPDATE and DELETE, with no erasure
  exception: §7.2 keeps acceptances through an erasure, and `chat.erase_account` anonymises the
  account row rather than deleting it. The account foreign key is ON DELETE RESTRICT, so an
  account that accepted can never be hard-deleted out from under its record. TRUNCATE is
  refused except in a test's cleanup (`chat.test_truncate`), as for PD-47/48/49/55.
  Consequence for ENG-10: a spec that records acceptances and then hard-deletes its accounts
  must first truncate `chat.terms_acceptance` in its cleanup transaction (add it to the
  harness's truncate list).
- **The database stamps the time** (`accepted_at`, `created_at`); a caller cannot backdate.
- **A-3 in the database too:** an acceptance of another kind's terms is refused by the guard,
  as a second line behind the API's "exactly the required set" check.
- **Publishing is idempotent for a retry** and refuses a changed version (publish a new one).
- **RLS fail-closed:** no request role writes either table or executes either writer; a
  signed-in account reads only its own acceptances (as PD-48's acknowledgements); versions are
  read by the server only.
- **The rollback refuses** while either table holds rows, unless the operator sets
  `chat.rollback_discards_terms` after exporting them: the rows are consent records.
