The owner approved A-3 (docs/release/google-play-blocker-roadmap-2026-11-03.md §7). Each account
accepts its kind's terms (`terms_family`, `terms_teacher`, `terms_staff`) and the shared
`code_of_conduct`. The wording, URLs and version names are pending (N-3): they are the owner's
configuration, never code or migrations.

Build: ENG-09 the data model (slot 20261107110000, renumbered on 2026-11-07 from 20261104110000; this branch); ENG-10..12 the API gate, the
Flutter gate and the Admin Web gate.

ENG-09 engineering decisions (the lead's to review):
- **Strictly immutable.** The acceptance guard refuses every UPDATE and DELETE, with no erasure
  exception: §7.2 keeps acceptances through an erasure, and `chat.erase_account` anonymises the
  account row rather than deleting it. The account foreign key is ON DELETE RESTRICT, so an
  account that accepted can never be hard-deleted out from under its record. TRUNCATE is
  refused except in a test's cleanup (`chat.test_truncate`), as for PD-47/48/49/55.
  Consequence for ENG-10: a spec that records acceptances and then hard-deletes its accounts
  must first truncate `chat.terms_acceptance` in its cleanup transaction (add it to the
  harness's truncate list).
- **The database stamps the time** (`accepted_at`, `created_at`); a caller cannot backdate.
- **A-3 in the database too:** an acceptance of another kind's terms is refused by the guard,
  as a second line behind the API's "exactly the required set" check.
- **Publishing is idempotent for a retry** and refuses a changed version (publish a new one).
- **RLS fail-closed:** no request role writes either table or executes either writer; a
  signed-in account reads only its own acceptances (as PD-48's acknowledgements); versions are
  read by the server only.
- **The rollback refuses** while either table holds rows, unless the operator sets
  `chat.rollback_discards_terms` after exporting them: the rows are consent records.

L-ENG-1 (2026-11-07): the developer guide's §1.3 proposals P-1 to P-4
(`docs/legal/developer-implementation-guide.md`) are folded into this migration, before it merges,
so no second migration or parallel table is needed:
- **P-1** `legal_document_version.content_sha256_ar` / `content_sha256_en`: required, exactly 64
  lowercase hex characters (one canonical form, so the release check in §6.3 compares strings).
  They are arguments of `chat.publish_legal_version`, and the idempotent re-publish compares them:
  the same URLs over different text are a changed version and are refused.
- **P-2** `terms_acceptance.method` (`signup` | `gate`): a required argument of
  `chat.accept_legal_documents`, with no default, so the API always says which flow it is. A repeat
  acceptance keeps the first row's method, as it keeps its time.
- **P-3** `legal_document_version.requires_reacceptance boolean not null default true`: an
  argument of `chat.publish_legal_version` (default true), compared on a retry. **Decision:** the
  guard refuses `false` for a document that has no version requiring acceptance yet, so a
  document's first version always requires it and ENG-10's required set is never empty. ENG-10
  still fails closed if it finds no requiring version at or before `legal.current.<key>` (for
  example, through `effective_at` ordering): it then requires the version in force.
- **P-4** confirmed: no IP address, user agent or device identifier on `terms_acceptance`; a test
  asserts the exact column list and the absence of network-address types.

New signatures (ENG-10 callers, including the local branch `claude/pd58-terms-api`, must follow):
`chat.publish_legal_version(document_key, version, url_ar, url_en, content_sha256_ar,
content_sha256_en, requires_reacceptance default true, effective_at default null, created_by
default null)` and `chat.accept_legal_documents(account_id, documents, client, locale, method)`.

ENG-10 the API gate and fail-closed configuration (2026-11-07, branch
claude/eng10-terms-gate-api-e328ae; ported from the unmerged local branch claude/pd58-terms-api and
brought to the P-1..P-4 model). The contract is `docs/contracts/API-CONTRACT.md` §1.1c. No migration:
the 20261107130000 slot the lead reserved is not used and not claimed.
- **Module** `apps/api/src/legal/`: `LegalService` (reads and decides, one query per request; writes
  ONLY through `chat.accept_legal_documents`), `LegalGuard` (global, after `AuthenticatedGuard` and
  `PermissionGuard`, before the action throttle), `@RequiresLegal()`, `LegalController`. No publish
  route: publishing is the owner's release process (`chat.publish_legal_version`, SQL).
- **The required set (P-3).** Per document, the version in force V (`legal.current.<key>`); the floor
  is the latest version with `requires_reacceptance` at or before V; the account is accepted when it
  accepted the floor or any later version. **Decision:** versions are ordered by `(effective_at,
  created_at, version)`, because a version name is the owner's free text and carries no order; the
  release process publishes each version in its own transaction (so `created_at` differs) or with its
  own `effective_at`. With no requiring version found, the floor is V (fail closed). Accepting takes
  only V: an older version is 409 `COMM.LEGAL_VERSION_STALE`.
- **Contract.** `GET /me`, login, refresh and password change carry `legal: {required: [...]}`.
  `GET /me/legal` adds, per document in force, `accepted`, `acceptedVersion`, `acceptedAt`.
  `POST /me/legal/accept {documents, client, locale}` records method `gate` (P-2); **decision:** any
  other body field is 400 `COMMON.VALIDATION`, so a client can never believe it named an account (the
  account is the token's). `GET /auth/signup/legal` (public) and `POST /auth/signup/verify`
  `acceptLegal` record method `signup` in the sign-up transaction (400 `COMM.LEGAL_REQUIRED` without
  it, when terms are in force). `client` and `locale` are required because §7.1 records them.
- **Accepting** takes the kind's own documents, no duplicates, at the versions in force, and must
  include every outstanding one; re-sending one already accepted is a no-op. Sign-up takes exactly the
  family set.
- **Configuration** is the `chat.config` rows (a JSON string, the owner's version name), not
  environment variables. Production (`APP_ENV=production`, API and worker) refuses to start when any
  of the four rows is missing, is not a string, or names an unpublished version. Outside production a
  missing row is a warning and that document is not asked for, so local, test and CI boot with no
  fixture (the PD-58 spec publishes synthetic `qa-*` versions on `jawwid.test` URLs and the harness
  truncates them). A row naming an unpublished version is 503 `COMM.LEGAL_NOT_CONFIGURED` everywhere.
- **Gated routes** (56; the list is in the contract): §7.4's list, plus `POST /reports` and
  `POST /me/blocks` (MG-1), plus four found by walking every ungated write on main:
  `POST /lessons/:id/report/edit` (a teacher rewrites the report card the family sees),
  `POST /lessons/:id/late-apology` (the family's words, as for `apology`),
  `POST /learners/:learnerId/rewards` (may carry the teacher's praise text) and
  `POST /certificates/:id/story` (publishes a Story to families). `test/unit/legal/legal-coverage.spec.ts`
  fails when a write rate-limited as a content action, or a route on its list, is ungated.
- **LD-11 (the lead, 2026-11-07):** a `child_safety` report is always accepted, even without
  acceptance: `@RequiresLegal({ except: 'child_safety_report' })` on `POST /reports`, the only
  exemption (the coverage spec pins it). Every other reason is gated; the body is still validated.
- **Staff.** §7.1 and §7.7 (1) gate every kind, so a staff account is gated on the same routes as a
  parent or teacher (messages, stories, certificate stories, calls). Staff-only workflow writes
  (tasks, cases, teacher files, evaluations, billing, intake, trials, moderation take/resolve,
  approving a held message) are NOT gated: they are staff duties, not content published to families,
  and gating moderation could hold up a child-safety case.
- **Left ungated on purpose:** deleting or withdrawing one's own content (message delete, reaction
  removal, story delete, report delete, reward undo, unblock), read/delivered/typing/presence, pin and
  star, one's own chat theme and wallpaper, notification settings, location, time zone, leave
  requests.
- A write that is not its own HTTP route calls `LegalService.assertAccountAccepted(accountId)`.
- **Existing accounts at go-live:** every account, existing or new, is asked at its next request once
  the versions are in force; there is no grandfathering. Open for the owner (not decided here).
- The integration harness truncates `chat.terms_acceptance` and `chat.legal_document_version` and
  removes the `legal.current.*` rows in the same transaction.
