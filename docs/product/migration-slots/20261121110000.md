PD-59: an active `trial_outcome` task follows the lead's current Sales owner (owner decision 2026-11-21).
Redefines `chat.work_task_trial_sales_owner` (owner, else Sales manager, else super admin) and adds the
trigger `trial_prospect_owner_moves_its_tasks` (open tasks only; audit `sales_lead.task_moved`).
Idempotent, additive. Rollback: `db/rollback/20261121110000_chat_pd059_trial_task_follows_owner.down.sql`.

**Apply**
- The file starts with `set local lock_timeout = '3s'`: CREATE TRIGGER takes SHARE ROW EXCLUSIVE on
  `chat.trial_prospect` (about 20 ms, no rewrite, nothing re-routes at apply). Without a bound, a writer queued
  behind it stalled others for the length of the first writer's transaction (measured 6 s). A timeout aborts and
  rolls the whole file back; it is safe to retry. The runner has no lock_timeout and a session pooler drops
  PGOPTIONS (ADR-014), so the bound is in the file.
- Requires 20261121100000 applied (it fails cleanly and rolls back otherwise).
- Deploy the API with or after the DB (the API sets `chat.sales_lead_actor`; without it a move is attributed to
  the system, nothing breaks).
- Re-running the file by hand on an already-migrated DB takes ACCESS EXCLUSIVE on `chat.trial_prospect` for
  `DROP TRIGGER IF EXISTS`; the runner skips applied files, so this only matters manually.

**No backfill.** An open task of a lead reassigned before this migration keeps its assignee until the lead is
reassigned again or the assignee leaves. Operator pre-check (informational; those tasks will NOT be moved, a
separate backfill would be needed):

```sql
select count(*) from chat.work_task t
  join chat.lesson l on t.source_key = 'trial_outcome:' || l.id
  join chat.trial_prospect p on p.id = l.prospect_id
 where t.kind = 'system' and t.state in ('open', 'awaiting_decision')
   and p.owner_staff_id is not null
   and chat.sales_lead_owner_eligible(p.owner_staff_id, p.organization_id)
   and t.assignee_staff_id is distinct from p.owner_staff_id;
-- and: select count(*) from chat.audit_log where action = 'sales_lead.reassigned';
```

**Rollback rule.** Roll back only if reassigning a lead errors or tasks move to the wrong people. Tasks already
moved stay moved (history and audit rows are append-only).

**Measured costs.** About 0.4-0.5 ms per changed prospect row; about 10 ms per single reassignment. A mass
reassignment of 42k leads would hold the sweep's advisory lock for about 23 s and could emit up to N pushes;
there is no bulk reassignment tool today.
