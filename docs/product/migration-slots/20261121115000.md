PD-59 / F7: `chat.message_card.trial_id`, a STORED generated uuid derived from `payload.trialId` (null when absent or
not a uuid), so the message read path can hide another Sales representative's trial card with one in-database
predicate. Nothing writes it. Rollback: `db/rollback/20261121115000_chat_pd059_card_trial_id.down.sql`.

## Cost: this is NOT an online migration
Adding a STORED generated column rewrites `chat.message_card` under ACCESS EXCLUSIVE. Measured by the independent
review at 5M cards: about 5 s of full chat freeze per 1M cards (every chat read AND every message send, because the
deferred constraint trigger `assert_card_message_has_card` references `message_card`), about 400 MB of WAL per 1M
cards (~2 GB at 5M), and the table's size again in free disk while it rewrites. The file starts with
`set local lock_timeout = '3s'`: that only bounds the WAIT for the lock (a timeout aborts and rolls the whole file
back, safe to retry); it does not bound the rewrite. The runner has no `lock_timeout` of its own, and a pooler drops
`PGOPTIONS`, hence the statement inside the file.

## Pre-check (production, read-only) and go / no-go
```sql
select count(*), pg_size_pretty(pg_total_relation_size('chat.message_card')) from chat.message_card;
```
GO at <= ~200k cards (about 1 s). NO-GO above ~300k cards unless the migration is switched to the no-outage
alternative below. Free disk must exceed the table's size.

## Deploy order and rollback order
- DEPLOY: migration FIRST, then the API. The new Prisma client selects `trial_id` on every `message_card` read, so
  API-before-migration breaks every card read.
- ROLLBACK: API FIRST (back to the previous build), then the down SQL. A rollback followed by a re-apply is a SECOND
  full rewrite with the same freeze.

## The no-outage alternative (not implemented; for the owner to choose once the production card count is known)
A plain nullable `trial_id uuid` column (`ADD COLUMN`, about 3 ms, no rewrite), filled at insert time by
`chat.guard_message_card` (derive it from `new.payload` on INSERT with the same regex-guarded cast), plus a batched
backfill of existing rows outside the migration (measured: 2M rows in 169 s without a freeze). It needs one more
statement in `guard_message_card`'s INSERT branch and a backfill script; the read path is unchanged (it already filters
on `trial_id`; a not-yet-backfilled row reads NULL, which fails closed, so representatives would briefly see fewer
trial cards, never more).
