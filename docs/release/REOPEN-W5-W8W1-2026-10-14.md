## 1. Authorized scope (verbatim intent) — and nothing else

1. Accept and verify legitimate LiveKit webhooks through the actual HTTP and authentication
   pipeline.
2. Capture and verify the `application/webhook+json` request body.
3. Enforce deactivation / revocation consistently for calls, pending notifications and related
   media access.
4. Push privacy: generic push text with no sender or caller name (owner decision 3).
5. The regression tests that prove 1–4.

Explicitly out of scope: the voice-call lifecycle, call routing, the VoIP activation gate
(`APNS_VOIP_ENABLED` stays OFF), CallKit / PushKit, other templates, unrelated notification
behavior.

## 2. The defects (verified before any change)

| Id | Defect | How it was verified |
|---|---|---|
| RT-038a | The global bearer guard (PR-B, after W5 closed) answered **401 to every LiveKit webhook** — LiveKit authenticates with its own signature, not a Jawwid token | live QA API: a correctly LiveKit-signed POST → `AUTH.UNAUTHENTICATED` |
| RT-038b | LiveKit posts `Content-Type: application/webhook+json`; no parser claimed it, so `rawBody` (the signed bytes) was never captured and **every real delivery was refused "no body"** | a real LiveKit 1.8.4 server's own deliveries to the QA API, logged as rejected |
| RT-037 | A deactivated person stayed in a live call room; a still-valid token (LiveKit admits ~60 s past `exp`) re-joined after removal; a push scheduled before a deactivation was sent after it; pushes named the sender / caller on the lock screen | real LiveKit 1.8.4 (local container); integration tests |

Consequence of RT-038: W5 media presence never updated in any running deployment.
