# PD-12 S1: supervision conversation, student certificates, teacher leave

Record: `docs/product/JAWUID-CHAT-PRODUCT-BOUNDARY.md` §4 PD-11 and PD-12.
Migration: `supabase/migrations/20261019090000_chat_pd012_s1.sql`.

## The teacher supervision conversation

Each teacher has one staff-only conversation with the Teachers department:
`chat.conversation.type = 'teacher_supervision'`, about one teacher
(`supervised_teacher_id`).

- **Who posts there:** the PD-12 tickets (certificate, leave) and PD-11's bonus
  and transfer-handover cards. `GET /teachers/:id/supervision-chat` (PD-11) opens
  this same conversation.
- **Members:** the teacher, plus the Teachers department's live
  conversation staff (its manager and members). Membership is synced every time
  the conversation is opened or a ticket lands in it. It decides only who is
  notified.
- **Access:** decided by `chat.staff_conversation_access`, in its own
  `teacher_supervision` branch. So the staff list, the RLS policies on
  `chat.message`, and `canRead`/`canSend` all agree. Operations supervisors, parents
  and other teachers have no basis on it.
- **Membership rules in the database:** never a contact; only the teacher it is about; staff
  only from the Teachers department (`guard_teacher_supervision_member`).
- **Creation:** lazily. It happens when the teacher files their first ticket,
  through `POST /me/supervision-conversation`, through
  `POST /teachers/:id/supervision-conversation`, or for everyone at once through
  `POST /supervision-conversations/ensure-all`.
- **Tickets:** `GET /conversations/:id/supervision-tickets` lists what the "+" menu
  offers there: `certificate` (with the teacher's learners) and `leave`. Only the
  teacher the conversation is about is offered anything.

## Student certificates

A student certificate is `chat.learner_certificate`. It is never a teacher's
qualification document.

| Step | Who | Route | Effect |
|---|---|---|---|
| request | the learner's assigned teacher | `POST /learner-certificates` | row `requested` + `certificate_requested` card in the supervision conversation (never the group) |
| list | Teachers dept, super admin (a teacher: own requests) | `GET /learner-certificates?state=` | `canDeliver` says whether a live group exists |
| upload | Teachers dept | `POST /learner-certificates/:id/upload` | a signed PUT URL. **The server picks the key**, inside the learner's group's namespace |
| issue | Teachers dept | `POST /learner-certificates/:id/issue` | the stored bytes are sniffed (PDF/JPEG/PNG/WebP, declared type and size) → `issued` → ONE `certificate_issued` card in the learner's group **carrying the file as its attachment**, plus a notice in the supervision conversation |
| decline | Teachers dept | `POST /learner-certificates/:id/decline` | `declined` + reason card in the supervision conversation; the family is not told |

The certificate is delivered to the same place as lesson cards: the learner's live
Student Group, or else a live family group about the learner that the
learner's teacher is in. The teacher and the parents are members there. The
existing media route serves the file to that conversation's readers, and to
nobody else (RT-037). No new teacher-app or parent-app surface was needed.

## Teacher leave

Leave lives in `src/leave` (its own module, so the dependency runs one way: it
uses lessons and the supervision conversation, and neither uses it). An approved
leave **is** its rows in PD-11's `chat.teacher_day_off`: the one record of days
off, which the scheduler and make-up booking already read, so an approved day is
unavailable the moment it is approved.

| Step | Who | Route |
|---|---|---|
| own balance + requests | the teacher | `GET /me/leave?year=` |
| request | the teacher | `POST /me/leave-requests` `{firstDay, lastDay, reason}` |
| withdraw (undecided only) | the teacher | `POST /me/leave-requests/:id/withdraw` |
| list | Teachers dept, super admin | `GET /teacher-leave-requests?state=`. Open rows carry `balance` and `collidingLessons` |
| approve | Teachers dept | `POST /teacher-leave-requests/:id/approve` `{days?, note?, cancelCollidingLessons?}` |
| decline (note required) | Teachers dept | `POST /teacher-leave-requests/:id/decline` |
| cancel approved (note required) | Teachers dept | `POST /teacher-leave-requests/:id/cancel` |
| one teacher's leave | Teachers dept, super admin | `GET /teacher-files/:id/leave?year=` |
| set allowance | Teachers dept **manager**, super admin | `POST /teacher-files/:id/leave-allowance` `{year, days, note?}` |

- **Balance** = the latest allowance for the year − the `teacher_day_off` rows in
  that year. It is computed on every read and never stored. A day off recorded
  directly (Teacher File, availability) counts too, because there is one record of
  days off, not two.
- **Approve** writes one `teacher_day_off` row per chosen day (default: every day
  of the request), linked through `leave_request_id`. A day already off is not
  written twice. The approver unticks the teacher's regular weekly day off, which is
  not leave.
- **Lessons inside the leave** are refused with `LEAVE_LESSONS_COLLIDE` unless
  `cancelCollidingLessons: true` is sent. With it, the leave is approved first. Each
  lesson is then cancelled through `LessonService.cancel` as `admin_cancelled`
  ("the teacher is on approved leave"), so each family gets its card. A lesson that
  could not be cancelled is reported in `notCancelled` and stays on the
  needs-action list. Such lessons never count as violations.
- **Cancel** removes the linked `teacher_day_off` rows for the days that have not
  passed (in `schedule.timezone`), which returns them to the balance; the audit log
  keeps the record. Cancelled lessons are not re-created.
- **Requests** stay inside one calendar year and are at most 62 days long. Open and
  approved requests never overlap (exclusion constraint).

## Card kinds are rows

PD-11 listed card kinds in a CHECK. A later migration that re-wrote that CHECK
would silently drop kinds another branch had added. Kinds are now rows of
`chat.message_card_kind` (FK). Add one with an `INSERT`.
