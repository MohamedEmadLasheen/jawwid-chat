# Rollback and recovery — 2026-10-14 migrations

Three migrations, each with its own down script. None reads, changes or deletes
existing table data in either direction (the RT-032 rollback keeps the journal table
and its rows).

| Forward | Down | What it changes |
|---|---|---|
| `supabase/migrations/20261014120000_chat_pd007_restore_br1_direct.sql` | `db/rollback/20261014120000_pd007.down.sql` | Replaces the bodies of 4 BR-1 functions (refuse any direct teacher/parent pair); adds trigger `message_br1_direct_guard` |
| `supabase/migrations/20261014140000_chat_rt031_call_notification_tenant.sql` | `db/rollback/20261014140000_rt031.down.sql` | Adds 4 tenant triggers on `chat.call`, `chat.call_participant`, `chat.notification` and the function `chat.enforce_actor_same_organization()` |
| `supabase/migrations/20261014150000_chat_rt032_revocation_journal.sql` | `db/rollback/20261014150000_rt032.down.sql` | Adds `chat.principal_revocation` (+ immutability guard), 8 ENABLE ALWAYS journal triggers on `account` / `contact` / `staff` / `teacher`, `chat.deactivate_principal()`, `chat.invoking_role()` / `chat.caller_is_server_side()` (identical to the staff-profile branch's) and one grant (`invoking_role` → `service_role`). Rollback drops the triggers, the trigger function and the operation and withdraws the grant; it keeps the journal (with its rows) and the two shared functions |

## Guarantees, as tested (disposable databases only)

Evidence: `migtest.sh` (session scratchpad), 20/20 checks.

- **Fresh build:** the complete history builds an empty database; `schema_acceptance`,
  `br1_invariants`, `relationship_predicate` and `story_rls` pass.
- **Upgrade in place:** a database at `20261013120000` holding PD-6-era data (a direct
  teacher/parent conversation with messages, a call, a notification) takes both
  migrations with the md5 of every conversation, member, message, call, participant
  and notification row unchanged. The PD-6-era call can still be ended; a new
  teacher message into that conversation is refused.
- **Re-application:** running either file again is a no-op (same function hashes, same
  data, no duplicate trigger).
- **Failure mid-migration:** `scripts/db/apply.sh` wraps each file and its ledger row in
  one transaction; an error inside the file leaves the old functions, no trigger and no
  ledger row.
- **Rollback:** both down scripts run under `psql -1` (all or nothing). After them the
  four BR-1 functions hash-equal the pre-upgrade database (the exact PD-6 bodies), the
  new triggers are gone, the data hash is unchanged, and the ledger rows are removed so a
  later re-forward applies cleanly (also tested).
- **Preconditions:** PD-7 refuses to run on a database without the PD-6 switch
  (`20260923140000`); RT-031 refuses without the organization columns and
  `chat.enforce_same_organization()`.

## Procedure

```bash
# RT-031 database guards (the API half of RT-031 keeps working without them)
psql -v ON_ERROR_STOP=1 -1 "$DATABASE_URL" -f db/rollback/20261014140000_rt031.down.sql

# PD-7 database half. A POLICY decision (return to PD-6), not a fix.
# Run from the repository root: the script includes the PD-6 migration by relative path.
psql -v ON_ERROR_STOP=1 -1 "$DATABASE_URL" -f db/rollback/20261014120000_pd007.down.sql
```

Roll back in reverse order of application (RT-032, then RT-031, then PD-7), and the API with them.

```bash
# RT-032 (re-opens RT-032; request roles may deactivate again where their grants allow)
psql -v ON_ERROR_STOP=1 -1 "$DATABASE_URL" -f db/rollback/20261014150000_rt032.down.sql
```

## What a rollback does NOT undo

- **Rows written while the migration was in force stay.** Nothing PD-7 or RT-031 refused
  was ever written, so there is nothing to restore; rows they allowed are ordinary rows.
- **The API.** At PD-7 the API refuses a direct teacher/parent pair on its own; rolling back
  only the database leaves the API stricter than the database, which is the safe
  direction but not PD-6. Return to PD-6 = roll back the API code too, on the product
  owner's instruction.

## What these checks do not prove

They ran on isolated containers built from this repository. **No production, staging or
shared database was accessed.** The production schema version, its data, and whether any
PD-6-era direct teacher/parent conversations exist there are **unverified**. Before applying
in production: confirm `chat.schema_migrations` contains `20260923140000` and
`20261013120000`, take the usual backup, and apply through `scripts/db/apply.sh`.
